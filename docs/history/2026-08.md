# 2026-08

## 2026-08-07 (parte 5) — PWA instalado abrindo em tela branca: lixo de `localStorage` que nenhum caminho apagava

O dono relatou o PWA instalado **não abrindo — só tela branca**, com internet e sem internet,
sobrevivendo a fechar o app por completo e reabrir. Suspeita inicial dele: cache alto por estar
instalado há muito tempo (embora o sistema reportasse só ~6MB).

Sem cabo USB (o celular não é reconhecido pelo PC), `chrome://inspect` estava fora. O diagnóstico
saiu de um teste que não precisa de cabo: **abrir o site numa aba normal e numa aba anônima do mesmo
celular**. No Android o PWA instalado divide storage e service worker com o Chrome, mas a anônima usa
partição limpa.

**Resultado: anônima abriu, aba normal ficou branca.** Isso descarta rede, CSP e build de uma vez —
o código que produção serve está bom — e prova que o problema é **estado local**.

### Causa raiz

Chaves `firestore_*` acumuladas no `localStorage` até estourar a quota. A cadeia, com cada elo
verificado no código:

1. Até 24/07/2026 o app usava `persistentMultipleTabManager`, que grava `firestore_clients_*` /
   `firestore_targets_*` pra coordenar abas (`src/firebase/config.ts`, comentário nas linhas 77-84).
2. Essas chaves só se limpam sozinhas num fechamento de aba limpo (`beforeunload`) — evento que um
   PWA no celular praticamente nunca dispara, porque o sistema mata o app.
3. A correção de 24/07 trocou pro `persistentSingleTabManager`. Isso parou de **criar** chaves novas
   e **não apagou nenhuma das existentes**.
4. Nenhum outro caminho do app apaga: `clearAccountLocalCaches` (`src/auth/logoutCleanup.ts`) filtra
   só `zerou.*`. A única função que remove `firestore_*` é a
   `recoverFromCorruptedFirestorePersistence`, que só roda quando o erro é capturado.
5. Quota estourada → as escritas de coordenação do próprio SDK falham → `INTERNAL ASSERTION FAILED`.
6. Esse erro nasce **assíncrono**, e error boundary do React não pega erro assíncrono. Não havia
   `window.onerror` nem `unhandledrejection` em lugar nenhum do `src/` (0 ocorrências) — então a
   recuperação automática, criada exatamente pra este erro, **estava inalcançável**.
7. Tela branca, muda, permanente. Anônima abre porque o `localStorage` dela está vazio. ✓

O install do dono é anterior a 24/07, então carregava o lixo desde antes da correção.

### A correção

`src/firebase/legacyStorageCleanup.ts` (novo) apaga as chaves `firestore_*` no boot. Chamado de
dentro do `getFirebaseServices()`, **imediatamente antes do `initializeApp`** — e isso é de propósito:
ali a ordem é garantida **por construção**, não por quem lembra de chamar primeiro no `main.tsx`. É
impossível o Firestore subir antes da limpeza, independente de quem chame `getFirebaseServices()`.

Sob single-tab essas chaves não têm leitor nenhum — são lixo puro. O cache offline de verdade mora no
IndexedDB e não é tocado. A sessão do Auth usa prefixo `firebase:authUser:`, não `firestore_`, então
também não é tocada (apagar deslogaria a pessoa) — há teste afirmando os dois.

### O que mais foi confirmado ao vivo (não é hipótese)

Produção está **saudável pra visitante novo**: `/app` renderiza a tela de login, e as 169 entradas do
precache do `sw.js` deployado resolvem todas com o content-type certo. Os 4 defeitos abaixo são reais
mas **não** eram a causa desta tela branca — três deles são o motivo dela ter sido **muda**.

**1. O hash do CSP nunca bateu — line ending.** `vercel.json` liberava
`sha256-jGB0f0cvbl+xdE1Ip3JRpEKaoAUtkyId78s8ZgZDqHA=`; o navegador em produção exigia
`sha256-fcfPa8XTbRDfoNCe/dSqWUYqidqexO3ztHo4dHU9PZ8=`. Medido nos dois sentidos:

```
copia de trabalho (CRLF, Windows)  1242 bytes -> sha256-jGB0f0cvbl+xdE...  <- o que estava no vercel.json
git / Vercel      (LF)             1219 bytes -> sha256-fcfPa8XTbRDfoNCe/  <- o que producao serve
```

`core.autocrlf=true` dá CRLF na cópia de trabalho, o git guarda LF (`git show HEAD:index.html` → 0
CRLF, 60 LF). O hash foi calculado do arquivo local. **O bootstrap de tema estava bloqueado em
produção desde `61bad23`** e nada acusava: build, typecheck e testes passam, e o único sinal era um
erro no console que ninguém tinha motivo pra estar olhando.

Este é o mesmo formato dos incidentes já documentados no `CLAUDE.md` (enum novo sem atualizar a
regra; `idempotencyKey` divergindo do id): **uma invariante entre dois arquivos que nenhuma ferramenta
verificava**. Seguida a lição que o próprio `CLAUDE.md` tira deles — *tornar a invariante impossível
de violar, não só testável*:

- `.gitattributes` fixa `index.html` em `text eol=lf`, então a cópia local passa a ser **byte-idêntica
  à que a Vercel serve** (verificado: o hash local agora é o de produção). Quem recalcular o hash à
  mão no Windows não erra mais.
- `src/test/cspInlineScriptHash.test.ts` recalcula o hash de **todo** script inline do `index.html`
  normalizando pra LF de propósito (é assim que o arquivo sai do git, independente do SO de quem
  editou) e afirma que o `script-src` libera cada um. Segundo teste impede `'unsafe-inline'` de voltar
  escondido. **Verificado que falha com o hash antigo e passa com o novo.**

**2. Fontes do Google bloqueadas** pelo mesmo commit: `style-src` não tinha `fonts.googleapis.com` e
`font-src` não tinha `fonts.gstatic.com`. Efeito só cosmético (cai pra fonte de fallback), mas era
erro real no console poluindo o diagnóstico. Liberados.

**3. Chunk que sumiu virava HTML com status 200.** O rewrite catch-all `"/(.*)"` do SPA engolia
também `/assets/`. Medido em produção:

```
GET /assets/index-DEADBEEF.js  ->  200  content-type: text/html
```

Um `<script type="module">` que recebe HTML falha ao parsear **sem erro acionável**. É exatamente o
que acontece com um PWA instalado há muito tempo cujo HTML em cache aponta pra um chunk que a Vercel
já não tem. Rewrite passou a `"/((?!assets/).*)"`: arquivo que sumiu agora dá **404 honesto**, e o
erro aparece. Deep link (`/app/dashboard`) continua caindo no rewrite normalmente.

**4. A recuperação automática do Firestore não alcança o erro pra que ela existe.** O
`firestoreRecovery.ts` (criado em 2026-07-24 pro crash `INTERNAL ASSERTION FAILED`) só é acionado
pelo `componentDidCatch` do `AppErrorBoundary`. Mas boundary do React **não pega erro assíncrono** — e
esse erro do SDK nasce assíncrono (entrega de snapshot, callback de IndexedDB). E `rg` por
`window.onerror` / `unhandledrejection` em todo o `src/`: **0 ocorrências**. Ou seja, a rede de
segurança estava inalcançável no caminho mais provável.

Somado a isso, o `AppErrorBoundary` estava **abaixo** do `AuthProvider` na árvore — justo o provider
que mexe com Firebase Auth, Firestore e IndexedDB. Provider quebrando acima do boundary = árvore
inteira sem montar = tela branca sem mensagem.

### O que mudou

- **`src/utils/globalErrorHandler.ts`** (novo): `window.onerror` + `unhandledrejection`, **primeiro
  import do `main.tsx` de propósito** — imports estáticos avaliam na ordem em que aparecem, então
  estar em primeiro lugar é o que garante que os listeners existem antes de qualquer outro módulo
  poder quebrar na avaliação. O boot em si virou `try/catch`. Quando `#root` está vazio, pinta uma
  tela com mensagem e **dois botões: "Recarregar" e "Limpar cache local"** — o segundo é a saída
  self-service que faltava (no incidente, a única saída conhecida era desinstalar o PWA).
- **`AppErrorBoundary` subiu pra cima do `AuthProvider`** (`src/App.tsx`).

### Regra nova: erro assíncrono nunca pinta tela de falha

Duas armadilhas encontradas ao escrever o handler, as duas quebrariam o app **offline**, que aqui é
operação normal e não erro:

- O `<link>` de fonte do Google falha sempre que o aparelho está sem rede. Um handler que trate
  qualquer recurso como fatal **cobriria com tela de erro um app que está funcionando offline**. Só
  conta `HTMLScriptElement` com `src` **da própria origem**.
- Promise rejeitada é **rotina** neste app: a regra offline-first manda gravar fire-and-forget. Por
  isso `unhandledrejection` só faz log e checa o caso auto-recuperável — **nunca** pinta tela.

Os dois casos viraram teste (`src/utils/globalErrorHandler.test.ts`, 6 testes), junto com "não cobre
UI já montada" e "não entra em loop quando a recuperação já foi tentada".

### Lição: limpeza pontual não conserta dado que já vazou

A correção de 24/07 estava certa e mesmo assim deixou o bug vivo por 2 semanas, porque tratou a
**fonte** (parar de escrever) e não o **acervo** (o que já estava escrito). Mesma forma do corolário
sobre truncar id que já está no `CLAUDE.md`: uma correção pontual não alcança o dado que já vazou.

**Regra**: quando um bug é "isto acumula sem nunca ser removido", trocar o produtor não fecha o caso.
Todo aparelho que rodou a versão antiga continua com o acervo, e num app offline-first ninguém vê —
não há erro na tela, não há log no servidor. A correção precisa de **duas partes no mesmo commit**:
parar de produzir *e* apagar o que já existe, num caminho que roda no boot de todo mundo.

### Validação

`npm run typecheck` limpo · **662 testes passando** (58 arquivos, +9) · `npm run build` ok · hash do
`dist/index.html` construído confere com o CSP novo. Lint continua com os **mesmos 52 problemas
pré-existentes** do `HEAD` (confirmado com `git stash`), nenhum nos arquivos tocados.

**Não deployado** — falta autorização do dono.

### Pra quem retomar

Depois do deploy, o aparelho deve se curar sozinho: o browser checa `sw.js` a cada navegação
(`Cache-Control: no-store` no `vercel.json`), o SW novo entra com `skipWaiting`/`clientsClaim`, e no
carregamento seguinte a limpeza roda no boot. Abrir o app **duas vezes**. Se ainda assim ficar branco,
limpar dados do site resolve na hora — e aí a hipótese do service worker volta pra mesa.

## 2026-08-07 (parte 2) — A causa real de "não dá pra pagar a fatura": id truncado ≠ chave

A correção da manhã não consertou o pagamento — ela fez o erro **aparecer**. O dono clicou e viu
`Missing or insufficient permissions.` na tela. Com isso na mão, a causa foi localizada e medida.

### A cadeia

`firestore.rules` (`validInvoiceLedgerCreate`, L1230) exige:

```
request.resource.data.idempotencyKey == entryId
```

O cliente derivava o id do documento a partir da chave com `idempotencyKey.replace(...).slice(0, 140)`.
E a chave de um pagamento era:

```
`${cardId}_${invoiceId}_${accountId}_${paidAt.getTime()}_${amountCents}` + '_payment'
```

Medido nas 4 contas reais do dono: **150 caracteres de chave, 140 de id**. Divergem ⇒ a regra recusa
⇒ o batch é atômico ⇒ **o pagamento inteiro cai**. E `fireWrite` engolia.

**Não era intermitente.** Pagar a fatura daquele cartão era impossível desde sempre — e é a origem
dos dois `permission-denied` que apareceram no console sem explicação e que eu não tinha conseguido
atribuir.

Duas causas independentes na mesma cadeia:

1. **`invoicePaymentTransactionId` reprefixava o `cardId`**, que o `invoiceId` já contém por
   construção (`invoiceIdFor` = `${cardId}_${referenceMonth}`) — 37 caracteres desperdiçados.
2. **O corte em 140 também podia COLIDIR**: duas chaves que só diferem depois do caractere 140
   truncam pro mesmo id, e o segundo lançamento viraria "duplicata" e desapareceria. É literalmente o
   defeito corrigido em **23/07/2026** nos ids de estorno de antecipação ("os ids de estorno colidiam
   por truncamento de string (140 chars) — corrigido trocando por um hash"), voltando por outro
   caminho porque a correção de julho foi pontual, não estrutural.

### As correções

- **Sistêmica**: `ledgerPayload` passou a derivar `idempotencyKey` **do próprio `id`**. É o único
  lugar do app que monta payload de ledger, então a invariante da regra ficou **impossível de violar**
  por sanitização ou truncamento, em qualquer escrita de ledger — não só no pagamento. O parâmetro
  `idempotencyKey` saiu da assinatura (4 call sites) pra não existir valor que possa divergir.
  `calculateInvoice` deduplica por esse campo e continua correto: id é único por definição.
- **Raiz**: `idempotentEntryId` foi pra módulo próprio (`src/cards/ledgerEntryId.ts`) e, quando a
  chave não cabe, o excedente vira **hash** (FNV-1a base36) em vez de ser jogado fora — id
  determinístico, único, com prefixo legível pra diagnóstico no console do Firebase.
- **Encurtamento**: a chave do pagamento não reprefixa mais o `cardId` (150 → 112 caracteres). O hash
  já protegeria, mas não chegar ao teto mantém o id legível.

### ⚠️ Por que os testes nunca pegaram — e a lição

O helper `ledgerPayload` do teste de regras montava **`idempotencyKey: entryId` à mão**. O payload de
teste satisfazia a invariante que o cliente violava.

**É o espelho exato do erro descrito na REGRA PRINCIPAL do `CLAUDE.md`**: lá o payload de teste era
*simplificado demais* e escondia uma regra desatualizada; aqui era *correto demais* e escondia um
cliente errado. Nos dois casos o teste testava a si mesmo.

E tem um detalhe honesto: minha primeira tentativa de regressão foi um teste de regras "aceita a
escrita com ids do tamanho real". **Ele passava com o bug restaurado** — testei. Depois da correção
sistêmica o cliente não consegue mais violar a invariante, então nenhum teste de regras pode falhar
por isso. O guarda tinha que ir pro lado do cliente:

- `src/cards/ledgerEntryId.test.ts` — duas chaves que diferem só depois do teto geram ids
  **diferentes** (falha com `slice`);
- `src/cards/cardService.test.ts` — todo lançamento que o cliente grava sai com
  `idempotencyKey === id`, e a chave do pagamento não repete o `cardId` (falha com a chave antiga);
- no teste de regras ficou só o lado da **regra**: ela precisa recusar um payload divergente.

Os três foram **verificados revertendo cada correção** — cada um falha sozinho, pelo motivo certo.

### Verificação

- `typecheck` ✅ · `npm test` **648** (+8) ✅ · `build` ✅ · `npm run test:rules` **114** (+2) ✅.
- Sem deploy: `firestore.rules` **não mudou** (a regra estava certa; o cliente estava errado).
- Medição que fechou o diagnóstico, feita na conta real via console do navegador: chave de 150 e id
  de 140 nas quatro contas (`Santander`, `Alelo`, `Carteira`, `Nubank`), com `iguais: false` em todas.

  confirmar pagando a fatura de ago/2026 (R$ 1.238,98).

## 2026-08-07 — Cartão: pagar fatura, janela em duas queries, 48x, histórico agrupado

Sessão longa, com dois bugs relatados ao vivo pelo dono no meio de um plano já aprovado. As duas
correções têm a mesma raiz cultural, e ela vale mais que os detalhes: **ausência de dado sendo
apresentada como fato**.

### 1. "Cliquei pra pagar a fatura e simplesmente não vai"

Confirmado por ele que **nada** aparecia no Extrato — nenhuma escrita. Cinco caminhos de falha muda
no mesmo fluxo, e o quinto só apareceu escrevendo o teste:

1. `if (!amount) return` **antes** de fechar o sheet, mostrar spinner ou mensagem. Com saldo em
   aberto 0 (ou ledger ainda carregando, que faz `calculateInvoice([])` devolver 0), o clique não
   escrevia, não fechava e não dizia nada.
2. `parseMoneyToCents` **lança** com texto não-numérico (`money.ts:51`), e exceção dentro de handler
   de clique não mostra nada pro usuário.
3. **Nenhuma confirmação de sucesso** — pagamento OK só fechava o sheet, então a pessoa repetia e
   caía em (1).
4. `recordInvoicePayment` usava `fireWrite` (catch vazio em produção) e, sendo `async` sem `await` no
   commit, resolvia na hora: os `.catch` das duas telas eram **código morto** e nenhum
   `permission-denied` chegava a ninguém.
5. O id idempotente do **FIN-03** vinha de `fromDateInputValue` = meio-dia com 0 ms. Mesma
   fatura/conta/valor no mesmo dia ⇒ id **byte-idêntico** ⇒ `allow update: if false` no ledger nega
   ⇒ batch atômico cai ⇒ engolido. **Nenhuma retentativa idêntica jamais podia funcionar.**

Correções: `recordInvoicePayment` devolve a promise (o sheet já fechou antes, offline-first intacto);
guardas viram mensagem dentro do sheet; botão só desabilita durante o envio (falta de conta agora
explica, em vez de botão morto sem motivo); confirmação de sucesso; e o instante do pagamento é
congelado na **abertura** do sheet — duplo clique reusa o id (FIN-03 preservado), reabrir gera id
novo, o que destrava a retentativa. Reusa o padrão que o `CardDetailPage` já tinha (`paidAtRef`).

### 2. "Dentro do cartão só aparece a fatura atual, e o limite nem tá contando"

O sintoma que mais ensinou. A aba **Cartões** mostrava o limite certo e **dentro** do cartão não —
essa assimetria é que localizou a causa: Cartões usa os totais **persistidos**, a tela do cartão
recalcula tudo do **ledger** (`mergeInvoicesWithLedger`).

`useInvoiceLedger` abre um listener por fatura (14 no cartão dele) e cada um tem
`LEDGER_BOOT_TIMEOUT_MS = 2500`, que marca a fatura como resolvida pro `loading` agregado **sem
dado** — isso é intencional e documentado. O que não era: `mergeInvoicesWithLedger` recalculava os
totais de **toda** fatura sobre os lançamentos em mão, sem checar se aquele ledger tinha chegado.
Pra fatura sem resposta isso é `calculateInvoice([])` = saldo 0 + status `'closed'`. Em cascata:

- limite usado **R$ 909,79** em vez de **R$ 5.902,31**;

⚠️ **Duas hipóteses minhas caíram antes desta**, e o registro importa: (a) "o ledger não está
chegando" — instrumentei e vi 14 de 14 entregando ledger completo; (b) "o filtro de transação
excluída está zerando" — `fetchDeletedTransactionIds` devolve "não excluída" em erro/ausência, é

### 3. A janela de faturas: uma query só cortava sempre o futuro

`subscribeInvoices` usava `orderBy('referenceMonth','asc') + limit(24)` = as 24 **mais antigas**. Num
cartão com mais de 24 faturas, o que não era baixado era a fatura atual e as futuras — o que o
Comprometido e a Análise de mês futuro precisam.

⚠️ **A primeira versão do plano estava errada e foi o dono quem derrubou**, perguntando o que
acontece com 48x hoje + outra 48x em 4 meses: **aumentar o limite não resolve**, porque com `asc` o
corte é sempre no futuro, em qualquer número (aquele cenário alcança ~52 meses de horizonte). O
conserto é estrutural — duas assinaturas por cartão, cada uma cortando do lado certo:

- futuro/atual: `where('referenceMonth','>=',mesAtual)` + `orderBy asc` + `limit 96` (rede de segurança)
- passado: `where('referenceMonth','<',mesAtual)` + `orderBy desc` + `limit 24`

O futuro **não é cortado** porque é limitado por natureza (no máximo o maior parcelamento ativo, e
encolhe sozinho); o passado é o lado que cresce pra sempre. O `limit(96)` é rede de segurança e
**sobe junto** se o teto de parcelas subir — está escrito no código, porque foi exatamente um limite
dimensionado no olho que causou o bug original.

Consequência de desenho: a ordem `asc` da exibição **não depende mais da direção da query**.
`useCardsData` ordena a união das duas janelas num lugar só. A correção de `b9cd0e6` (24/07, fatura
futura no topo) continua valendo, agora por ordenação explícita em vez de coincidência.

### 4. Âncora derivada da transação — o que destravou o 48x

transação: `installmentStart === 1` (compra já em andamento nunca desloca) e `diff === 1` exato.

**Critério de segurança respeitado**: nenhum teste existente mudou de resultado (625 antes, 625

### 7. A aba de faturas pagas — e por que o mês nunca ia funcionar

Depois de pagar a fatura com sucesso, o dono voltou: *"percebi que não foi nada para nenhum grupo,

seja a fatura de agosto fechou no dia 2 e foi paga no dia 7 — dentro do próprio mês de referência. O
critério `outstandingBalanceCents > 0 || referenceMonth >= mês corrente` mantinha ela em "a pagar" por
causa do segundo termo (`'2026-08' >= '2026-08'`), e como nenhuma outra fatura era passada+zerada, o
grupo "quitadas" ficava vazio — e grupo vazio não é renderizado, então não apareceu aba nenhuma.

Eu tinha construído o critério pensando em fatura "do mês passado paga", que é o caso que aparece
depois. Mas **fatura fecha e é paga dentro do próprio mês**: o mês de referência nunca ia distinguir
"paga" de "a pagar" no único momento em que isso importa, que é logo depois de pagar.

- **Critério novo**: `settled` = saldo zerado **e** (`paymentsTotalCents > 0` **ou** mês passado). O
  pagamento é o que tira a fatura da lista; o mês virou só o secundário, pro passado zerado por outro
  caminho (crédito, estorno, dado legado sem pagamento registrado). Fatura **futura vazia** continua em
  "a pagar" — saldo zero sem pagamento é fatura vazia, não fatura paga, e quem esconde futura vazia é
  `invoiceHasVisibleActivity`. Continua sem depender de `status === 'paid'`, pelo motivo da parte 6.
- **Fatura corrente ANTECIPADA passa a contar como paga**, porque antecipar grava pagamento de verdade
  (`recordInvoicePayment(..., advance: true)`). Ela continua no topo da tela como "Fatura atual"
  (`pickCurrentInvoice` olha o ciclo, não este agrupamento) — só sai da lista. Se uma compra nova cair
  nela, o saldo volta a subir e ela volta pra "a pagar" sozinha.
- **Grupo recolhido virou ABA.** *"Depois de cinco faturas pagas eu já vou ter que ficar arrastando a
  tela pra baixo pra poder ver as que eu preciso pagar."* Mesmo recolhida, a seção somava altura no fim

  Abre sempre em "A pagar". "Ver mais faturas" mudou pra dentro da aba "Pagas". O h2 deixou de ser
  "Histórico de faturas" (com uma aba "A pagar", "histórico" mentia) e virou "Faturas do cartão".
- **A aba corta leitura de verdade**, que era metade do pedido dele (*"ela ia tirar a leitura da fatura
  que já foi paga"*): `ledgerTargets` assina o ledger **só das faturas em aberto**. Em dois anos de uso
  são ~24 assinaturas por abertura da tela, pagas pra renderizar linhas "Paga · R$ 0,00". Seguro porque

  exatamente o instante em que ainda vale olhar o ledger dela. Não há laço: a assinatura só depende do

## 2026-08-06 (parte 4) — As 2 divergências residuais fechadas com campo espelho + a Vic alinhada

### Por que faltava um campo, e não um `if`

As duas divergências tinham a mesma raiz: **informação que só existia no ledger da fatura**, e o
"Resumo de gastos" do Dashboard não lê ledger de propósito (custo por abertura, ver parte 2).

- `anticipateInstallments` (`cardService.ts`) gravava **só** lançamentos no ledger — crédito na
  fatura da parcela antecipada, débito na fatura atual — e **nada** na transação. Quem não lê ledger
  não tinha como saber que a parcela mudou de mês.
- `registerOngoingInstallments` gravava `installments` = quantas **faltam**, mas não o número real
  da primeira ("7 de 10"). A reconstrução numerava de 1, criava uma **parcela 1 falsa** e disparava
  o deslocamento de `installmentShiftBySource` — que a Análise, lendo o ledger real (sem parcela 1),
  nunca aplica.

Correção: **dois espelhos na transação**, com `firestore.rules` e `npm run test:rules` no mesmo
commit, pela REGRA PRINCIPAL do `CLAUDE.md`.

| campo | quem grava | forma |
|---|---|---|
| `installmentStart` | `registerOngoingInstallments` | int (o "7" de "7 de 10") |
| `anticipatedInstallments` | `anticipateInstallments` | mapa `mês da fatura` → `mês em que se antecipou` |

Detalhes que não são acidentais:

- **Chaveado por mês da fatura, não por número de parcela**: crédito de dado legado pode não ter
  `installmentNumber`, e o mês é o que a reconstrução conhece de cada parcela.
- **Chave pontilhada no update** (`anticipatedInstallments.2026-11`): quem antecipa duas vezes na
  mesma compra, em meses diferentes, não perde o primeiro registro.
- **`installments` e `installmentStart` ficaram FORA da lista de campos atualizáveis** da regra: o
  cronograma de uma compra não se edita (regra de 2026-07-23 — valor/parcelas/cartão errados exigem
  excluir e relançar). Só `anticipatedInstallments` entrou no update. Tem teste travando os dois.
- A regra valida `anticipatedInstallments is map` com teto de 72 (o mesmo de `installments`) e
  comenta que é **cache de exibição** — a verdade continua no ledger, que só a Cloud Function muda.

## 2026-08-06 (parte 3) — Categoria do "Resumo de gastos" leva pro Extrato filtrado

**Pedido do dono**: *"seria incrível, se eu pudesse no resumo de gastos... clicar nelas, e quando eu

### Armadilha 1: categoria-mãe abriria lista VAZIA

O filtro do Extrato era igualdade estrita (`t.categoryId !== categoryFilter`), e a parte 2 desta

O parâmetro só **semeia** o estado inicial (`useState` com initializer). Se ele ficasse na URL depois
de a pessoa limpar o filtro, um F5 ressuscitaria o filtro que ela acabou de tirar — então
`changeCategoryFilter` remove o parâmetro com `replace: true`. O filtro também chega **visível**: o
badge "Filtros · 1" já contava `categoryFilter`, e o sheet mostra "Categoria: Lazer".

### A correção: reconstruir o cronograma, não a regra

O número certo exige saber **em que mês cada parcela cai** — informação que mora no ledger da
fatura, e ledger no boot é o custo que a parte 1 desta mesma sessão recusou (listener reconectado
depois de 30 min é cobrado como query nova; num PWA isso é custo por abertura).

A saída veio de três dados que **já estão na transação**, descobertos lendo `cardService.ts`:

1. **`installments`** — quantas parcelas o ledger tem pra essa compra. Em compra já em andamento
   (`registerOngoingInstallments`) é quantas **faltam**, e `amountCents` é o que **falta** — então
   `installmentAmounts(amountCents, installments)` acerta o valor da parcela nos **dois** tipos de
   compra, sem caso especial.
2. **`invoiceId`** — a fatura da primeira parcela. E `invoiceIdFor` monta o id como
   `` `${cardId}_${referenceMonth}` ``, então **o mês da primeira fatura está dentro do próprio
   id**. Isso é o que faz a correção custar zero: nem os documentos de fatura são necessários, e o
   card **não volta a esperar o cartão sincronizar** (o fix de 25/07 continua valendo).
3. **`resolveInstallmentCycle(..., index)`** põe a parcela `n` em `primeiraFatura + (n-1)`, meses
   consecutivos — daí basta somar o índice.

`invoicesForSpendingFromTransactions` (`src/cards/installmentSchedule.ts`, novo) devolve
`InvoiceForSpending[]` — o mesmo formato que a Análise passa — e o Dashboard chama a
`spendingByCategoryForMonth` de verdade, mais `rollUpByParent`, com o mesmo filtro `> 0` e a mesma
ordenação.

⚠️ **Isto não é uma segunda implementação da regra de gasto, e a diferença importa**: nenhuma
decisão de "em que mês esta parcela conta" acontece no arquivo novo. O deslocamento da parcela 1
(`installmentShiftBySource`) continua sendo calculado **dentro de `spendingAnalysis.ts`**, a partir
da parcela 1 sintetizada — não recalculado. Estorno, conta "fora do saldo", tag de meta/cofrinho,
antecipação: tudo segue vindo de lá. O arquivo novo só responde "quais parcelas existem, de quanto,
em qual fatura".

`installmentAmounts` **saiu de `cardService.ts` pra o módulo puro novo** em vez de ser copiada — os
dois consumidores (quem grava as parcelas e quem as reconstrói) precisam do mesmo arredondamento
exato (1 centavo a mais nas primeiras `resto` parcelas). Copiada, uma divergência de centavos
apareceria mais tarde, do tipo que ninguém investiga e todo mundo desconfia.

### As divergências que SOBRAM, enumeradas de propósito

Estão na doc da função, e duas viraram item no `docs/planning/TODOS.md`:

1. **Antecipação de parcela** — a Análise move o gasto pro mês em que se antecipou (decisão do dono

2. **Compra "já em andamento" com a próxima parcela caindo exatamente 1 mês depois da data da
   compra** — a transação guarda quantas parcelas faltam, não o número real (7/10), então

4. **Tarifa, juros e estorno de fatura** — só existem no ledger. Já era assim antes; o Dashboard

Nenhuma delas é o caso comum, que era exatamente o que estava errado antes.

## 2026-08-05 — Análise: a parcela de cartão passou a contar no mês da COMPRA

**Relato do dono** (usando o app, não testando): *"comprei um jogo de R$135 e entrou na análise, foi
pelo cartão de crédito. Mas no mesmo dia, ontem, fiz a compra de um presente e não foi para a
análise. Isso era o esperado?"*. Depois, ao entender a regra: *"ambos vão ser pagos na mesma fatura.
Fica confuso, um aparece em agosto e outro só em setembro sendo que é a mesma fatura do cartão?"*

Ele estava certo. Não era bug de dado — era incoerência de modelo.

### O que estava acontecendo

Desde **2026-07-28** a Análise usa duas réguas:

| | Onde contava |
|---|---|
| compra à vista | mês da **compra** (transação, `cashMonth`) |
| compra parcelada | mês da **fatura** (ledger, `referenceMonth`) |

Cada metade se defende sozinha. À vista é um evento num instante só, e a data da compra é a única
data que significa algo — usar a fatura seria sorteio (dependendo do fechamento, o mesmo gasto vira
julho ou agosto). Parcelada já nasce espalhada e o ledger já tem uma âncora por parcela, de graça.

**O problema é que as duas âncoras estão deslocadas ~1 mês uma da outra**, e quem produz o
deslocamento é o dia de fechamento: `resolveInstallmentCycle` (`cardDates.ts` L59) manda a compra
pra fatura do mês seguinte quando `purchaseDay >= closingDay`. O Nubank dele **fecha dia 2** — 28
dos 30 dias do mês caem depois do fechamento. Pior caso possível.

Se o cartão fechasse dia 30, as duas réguas concordariam e ninguém teria notado nada. Ou seja: o
defeito não era o híbrido, era **a parcelada começar um mês tarde**. As parcelas 2, 3, … já estavam
espaçadas certo.

### A correção: deslocar a série, não recalcular datas

`installmentShiftBySource` calcula um deslocamento por compra e subtrai do `referenceMonth`:

```
mesAncorado(entry) = referenceMonth − shift(sourceTransactionId)
shift = 1  ⟺  existe `purchase` com installmentNumber === 1
              E  monthDiff(referenceMonth dela, mês da compra) === 1
```

Recalcular o mês a partir de datas seria mais direto e **teria quebrado dado real** — ver abaixo.

**Duas travas independentes**, as duas de propósito:

1. **A âncora é `installmentNumber === 1`, não "a menor parcela presente".** Compra cadastrada por
   `registerOngoingInstallments` (a que já estava rolando antes do app) começa na parcela 7, 8, 11…
   e **nunca** tem parcela 1 — então nunca desloca. Elegê-la pela menor presente moveria essas
   compras um mês inteiro sem motivo.
2. **Lista branca `diff === 1`, não `clamp(diff, 0, 1)`.** Este era o bug do meu primeiro desenho, e
   o agente de plano o pegou: `clamp(8, 0, 1)` devolve **1**, não 0 — exatamente o caso do
   `registerOngoingInstallments` (compra em janeiro, parcela 7 na fatura de setembro → diff 8).
   A garantia que eu queria ("nenhum gasto se move mais de 1 mês") o `clamp` dava; a que faltava era
   "nenhum gasto se move **sem motivo**".

Efeito combinado: dado antigo, dado torto e dado incompleto caem todos no comportamento de antes.

### Antecipar parcela continua movendo o gasto — mas ancorado no dia da antecipação

Decisão do dono, contra a minha recomendação inicial: *"se eu antecipei, gastei naquele mês. A
análise mostra o que saiu de dinheiro naquele mês"*. Exemplo que ele deu, compra em 5x:

| | jan | fev | mar | abr | mai |
|---|---|---|---|---|---|
| parcelas | 100 | 100 | 100 | 100 | 100 |
| créditos das antecipadas | | | | −100 | −100 |
| débitos (2× em março) | | | +200 | | |
| **total** | **100** | **100** | **300** | **0** | **0** |

**Meu argumento contra estava errado, e vale registrar.** Eu disse que isso faria "um mês passado
mudar de valor". Não faz: `collectFutureInstallments` (`anticipation.ts` L76) só oferece parcelas de
faturas com `referenceMonth > currentInvoice.referenceMonth` — antecipar **nunca alcança um mês já
fechado**, só projeção futura.

E "deixar como estava" **não produziria essa tabela**: o débito da antecipação caía na fatura ATUAL e
era contado pelo `referenceMonth` dela — antecipando em março depois do fechamento, apareceria em
abril. O mesmo erro de 1 mês. Por isso `anchoredMonthOf` tem **uma exceção**:
`installment_anticipation` conta pelo `effectiveAt` (o momento em que se antecipou).

O **crédito** (`installment_anticipation_credit`) não precisou de exceção nenhuma: ele mora na mesma
fatura da parcela que anula, então herda o mesmo deslocamento e zera o mês certo por construção —
inclusive em dado legado sem `installmentNumber` no crédito.

### Compra excluída: casar por compra, não por lançamento

`reverseCardPurchaseOnDelete` grava o `purchase_reversal` com `effectiveAt: now` (a hora da
exclusão) e **sem `installmentNumber`** — só copia tipo, valor, cartão, fatura e

## 2026-08-03 (parte 3) — Revisão completa do modo casal: 3 bugs relatados, 2 achados piores

Pedido do dono depois de criar um espaço compartilhado e testar com as duas contas: *"tem que fazer

### O bug de "sair do espaço": a regra e o cliente discordavam sobre QUANDO você ainda é membro

Relato: *"eu fui o convidado e ao tentar sair do espaço compartilhado deu que eu tenho permissões
insuficientes para sair"*.

`leaveCoupleWorkspace` (`sharedService.ts`) monta um batch com quatro escritas: member doc →
`status: 'removed'`, workspaceRef → `removed`, workspace → `partnerUserId` vazio, e **um log de
auditoria**. As três primeiras estavam certas. O problema era a quarta, contra esta linha de
`validAuditLogCreate`:

```
&& getAfter(currentMemberDoc(workspaceId)).data.status == 'active'
```

`getAfter` é o estado **depois** do batch. Quem está saindo é `removed` depois do batch, por
definição — então o log era negado, e como batch do Firestore é atômico, **a saída inteira caía**. O
erro que chegava na tela era o genérico de permissão, apontando pra "sair", não pro log.

Por que só o convidado sofria: `removePartner` faz as mesmas escritas, mas o autor é o **dono**,
cujo member doc não é tocado — `getAfter` vê ele ativo e o log passa. Um caminho o dono testou à mão
no papel de dono; o outro, nunca.

Correção: um ramo novo, estreito de propósito — o log de saída é aceito quando o autor estava ativo
**antes** (`get`) e está `removed` **depois**, e só pro tipo `member_left_workspace` com
`targetId == request.auth.uid`. Tem teste garantindo que um log de **outro** tipo no mesmo batch
continua negado, pra o ramo não virar porta dos fundos.

**Verificado desligando o ramo e rodando o teste**: `7 PERMISSION_DENIED`, o mesmo erro do app.

### "Quem deve quanto a quem" era sempre zero — e o acerto inteiro era código morto

Isso não estava na lista do dono. `useSharedWorkspaceData` calculava `balances` e
`settlementSuggestion` a cada snapshot, assinava a coleção `settlements` **em toda abertura da tela**
(leitura paga) — e **nenhuma tela renderizava nada disso**. `createSettlementProposal`,
`acceptSettlement` e `recordSettlementPayment` existiam no serviço sem um único caller de UI.

Pior: mesmo se alguém tivesse renderizado, o número seria zero. `calculateSharedBalances` contava só
despesa com status `accepted`/`settled`; `createSharedExpenseClaim` cria tudo como `pending`; e não
havia tela pra aceitar. O ciclo nunca fechava, por construção.

Decisão: **inverter o default**. `pending` passa a contar (quem espera pelo aceite é justamente quem
já pagou — esperar não pode ser pré-requisito pra dívida existir) e **contestar** (`disputed`) é o
que tira do acerto. Isso também resolveu os dados legados sem migração nenhuma.

O acerto ganhou tela (`CoupleSettlementSection.tsx`), com uma restrição que veio da arquitetura, não
de gosto: **cada pessoa só lança o próprio lado**. A transação do parceiro vive no workspace pessoal
dele, onde ninguém mais é membro — as regras recusariam, e é assim que a privacidade se sustenta.
Então: quem deve usa "Já paguei minha parte" (cria o acerto + a despesa na conta dele), e quem
recebe vê "X registrou um pagamento de R$ Y" e usa "Recebi" (lança a entrada na conta dele). Casa
com a regra de voz do app — o Granativa não move dinheiro, a pessoa confirma um fato passado.

`receiptConfirmedAt` é gravável **uma vez só** (a regra recusa sobrescrever): é o que impede a mesma
entrada de cair duas vezes na conta de quem recebeu. A regra de create de `settlements` também
relaxou pra aceitar o acerto nascer já pago — mas só pra quem pagou (`fromUserId` é o autor) e com o
status batendo com o valor, senão daria pra criar "quitado" pagando R$ 1.

### A despesa dividida agora é lançamento de verdade — pelo TOTAL, não pela metade

Relato: *"a pessoa coloca a despesa mas não indica qual conta vai ser debitada, essa despesa também
tem que ir para as transações, vai entrar nas análises, então tem que escolher categoria e tudo"*.

A sheet ganhou **data, conta e categoria**, e o registro virou um batch atômico cross-workspace
(doc do casal + transação pessoal + saldo da conta) — o mesmo padrão que `coupleGoalDeposit` já
usava desde o cofrinho.

**O valor debitado é o total, não a parte de quem registra.** Decisão do dono depois de eu apresentar
as duas leituras: foi o total que saiu do banco, e lançar metade deixaria o saldo da conta
permanentemente acima do saldo real — exatamente a divergência que a tela "Acertar saldo com o
banco" existe pra consertar. A parte da outra pessoa não se perde: vira dívida dela no acerto.

**O vínculo entre as duas pontas é derivado, nunca gravado.** O id da transação pessoal é
`personalTransactionIdForShared(claimId)` — função pura do id compartilhado. Isso não é elegância
gratuita: já existia teste de regra provando que um `sourcePersonalTransactionId` dentro do claim é
**recusado** (o `hasOnly` mantém isso de pé), porque um ponteiro pra dado pessoal no espaço a dois
fura a privacidade. Derivar dá o mesmo resultado com zero vazamento — e de brinde deixa a criação
idempotente. Excluir a despesa faz `getDoc` da transação derivada (1 leitura, só nesse caminho) e
desfaz as duas pontas junto, com o saldo voltando.

Campo novo `occurredOn` no claim: a lista do casal e a transação pessoal usam a **mesma** data,
senão o mês da Análise divergiria do que os dois veem no espaço. Regra e payload de teste
atualizados no mesmo commit, como manda a REGRA PRINCIPAL do `CLAUDE.md`.

Excluir ficou **só pra quem registrou** — é a única pessoa capaz de desfazer as duas pontas. Se o
outro pudesse apagar só o lado compartilhado, a transação pessoal ficaria órfã no extrato de quem
pagou e ninguém mais conseguiria limpar. Quem não registrou tem "Contestar", que tira do acerto sem
apagar nada.

### O modo casal virou a única parte do app que exige internet

Pedido explícito do dono: *"por se tratar de duas pessoas ele não pode ser usado sem internet em
hipótese nenhuma... se um tiver com internet lenta e outro com a internet boa vai dar divergência"*.

Isso contradiz a REGRA PRINCIPAL do projeto (offline-first) **de propósito e só aqui**, e o motivo
cabe numa frase: offline-first pressupõe **uma** pessoa por dado. No espaço pessoal a fila local
nunca briga com ninguém. No espaço a dois são duas filas subindo em momentos diferentes na mesma
coleção — dá duplicata invisível e, pior, acerto calculado sobre um saldo que já mudou no servidor
quita dívida que não existe mais.

`src/shared/coupleWriteGate.ts` (novo) bloqueia por dois sinais:

- **offline** (`navigator.onLine`, via o `useIsOnline` que já existia);
- **conexão ruim**: escrita pendente há mais de 8s sem o servidor confirmar. A medida vem do
  `hasPendingWrites` dos próprios snapshots — não de `navigator.connection` (heurística de banda,
  mente em 4G ruim) nem de requisição extra pra medir latência. Escrita confirmada some da fila em
  milissegundos numa rede saudável.

Vale pra **tudo** que grava no espaço a dois, incluindo o cofrinho (que também é dado dos dois) e
gerar/revogar convite. Aviso em `.notice--warning` (variante nova: nem `danger`, que diria
"quebrou", nem `success`, que diria o oposto) **antes** de a pessoa tentar, mais `disabled` nos
botões, mais guarda síncrona nos handlers — porque o estado da conexão pode mudar entre o render e o
toque. Leitura do cache continua livre: dado que já veio aparece normalmente.

Junto disso, as escritas do casal deixaram de passar por `fireWrite` e voltaram a **devolver a
promise**. `fireWrite` engole erro de propósito (offline-first, não expor erro técnico), mas aqui
escrita recusada em silêncio é divergência entre duas pessoas — a UI fecha a sheet na hora do mesmo
jeito, só que com `.catch` mostrando mensagem amigável.

## 2026-08-03 (parte 2) — "Salvar transação" saía da tela sem gravar: validação que existia e ninguém via

Relato do dono, e ele já tinha isolado o comportamento sozinho: *"se eu colocar valor mas não
colocar conta ou cartão ele deixa registrar, **não salva nada, mas deixa registrar**"*.

### A validação não estava faltando — estava inalcançável

O primeiro instinto ("falta validar") estava errado, e é o registro mais útil desta sessão. As duas
regras já existiam, escritas e corretas, em `financeSchemas.ts`:

```ts
description: z.string().trim().min(2, 'Informe uma descrição.').max(120),
accountId:   z.string().trim().min(1, 'Escolha uma conta.'),
```

O que falhava era **onde** elas rodavam. `createTransaction` é `async` e chama `schema.parse` dentro
do corpo, então um erro de validação não é `throw` síncrono: vira **promise rejeitada**. E a página
fazia isto:

```ts
try {
  createTransaction(...);            // sem await, sem .catch
  navigate('/app/transactions');     // roda SEMPRE
} catch (error) { /* nunca alcançado */ }
```

`try/catch` não pega rejeição de promise que ninguém esperou. Então a sequência real era: Zod
reprova → rejeição não tratada → `navigate` acontece mesmo assim → a pessoa cai no Extrato e o
lançamento não está lá. Zero mensagem, zero rastro. A rejeição não tratada também não aparecia pra
ninguém, porque `createTransaction` estava **sem `.catch`** — a compra no cartão, logo acima no
mesmo arquivo, já tinha o dela; só o caminho de transação normal não.

**A regra que fica**: num app offline-first, onde escrita é fire-and-forget de propósito, o schema é
a **rede de segurança do dado, nunca o primeiro lugar onde um erro previsível aparece** — lá ele é
estruturalmente invisível. Toda condição que a pessoa consegue corrigir na tela precisa ser
conferida de forma **síncrona, antes de disparar a escrita**, em português. É a mesma família dos
incidentes de `firestore.rules` já registrados no `CLAUDE.md`: validação correta, num lugar que o
padrão fire-and-forget faz calar.

### O que entrou

- Guardas síncronos pra conta/cartão, conta de origem e destino da transferência — cada um com a
  mensagem no contexto certo ("Escolha a conta ou o cartão dessa despesa" vs. "...onde o dinheiro
  entrou").
- **Valor zero passou a barrar.** `moneyCentsSchema` aceita `0` (é `min(0)`, não `min(1)`), então
  valor em branco gravaria um lançamento de R$ 0,00 — válido pro schema, lixo pro usuário. Não
  estava no pedido, mas **a mudança do título tornou esse caminho mais fácil de alcançar**: o
  `min(2)` da descrição era, sem querer, o que barrava o registro vazio por acidente. Tirar uma
  trava obriga a olhar o que ela estava segurando de carona.
- O `try/catch` enganoso saiu (ele documentava uma proteção que não existia), e o `.catch` que
  faltava entrou.

### Título: opcional, com herança anunciada

Pedido: *"ao invés de deixar o obrigatório, queria que ao deixar sem título ele colocasse o nome da
categoria"*. Cadeia: **digitado → nome da categoria → rótulo do tipo**. O último degrau existe
porque categoria é opcional no schema; sem ele, "sem título e sem categoria" voltaria a ser uma
gravação recusada em silêncio — exatamente o bug que a sessão estava fechando.

A dica embaixo do campo é **viva**, não estática: escolher "Delivery" muda o texto pra *"Em branco,
usamos Delivery."*. Título aparecendo preenchido no Extrato sem nenhum aviso na hora de lançar
pareceria dado inventado pelo app — e o custo de anunciar é uma linha de texto que já estava vazia.

### O retângulo no valor

*"Sempre ao colocar o valor fica um retângulo em volta, não quero isso."* A causa é uma sutileza de
CSS que vale registrar: **`input` de texto casa com `:focus-visible` sempre que recebe foco**, não
só em navegação por teclado (é o comportamento correto por spec — digitar é a interação esperada).
Com `autoFocus` no campo, a moldura aparecia já na abertura da tela, emoldurando o número que o
próprio design system elege como herói.

Simplesmente apagar o `outline` seria regressão de acessibilidade, então ele virou um **sublinhado**
sob o valor (`.amount-hero-input-wrap`, `border-bottom` + `:focus-within`): sem moldura, mas com
indicador de foco — e de quebra o campo passou a *parecer* um campo antes de ser tocado, o que a
versão anterior só revelava depois do foco.

### Uma correção de UX que a própria correção exigiu

Os guardas mandam a mensagem pro `FormMessage`, que vive no **topo** do formulário — e o botão
"Salvar transação" é **fixo no rodapé** (`.entry-actions`). Com a tela rolada pra baixo, apertar
Salvar mostraria a mensagem fora da vista: um erro silencioso trocado por outro. Por isso `fail()`
faz `scrollIntoView` na mensagem. Detalhe pequeno que anula o valor do resto se faltar.

## 2026-08-03 (parte 4) — Projeção mostrava saldo R$ 0,00 offline: metade da carta vinha do cache, metade ao vivo

Relato do dono: *"ao abrir o app sem internet ela fica com valor 0"*, apontando o termo do saldo
(🐷) dentro da fórmula da carta "Projeção do próximo mês".

### Por que era permanente, e não um piscar

O Dashboard tem um cache de exibição (`dashboardViewCache`) que pinta a última tela conhecida
enquanto os listeners não respondem. Todos os números da carta saíam dele — **menos um**: o saldo
da fórmula lia `dashboard.totalBalanceCents`, o valor **ao vivo**.

Isso seria um flash de milissegundos no boot normal. Offline a janela cresce muito, e há **dois
caminhos** pra isso (corrigido depois da varredura — no commit original eu descrevi só o segundo,
como se fosse o único):

1. **O caminho comum**: `loading` só vira `false` quando **todas as 7 coleções** entregam o primeiro
   snapshot — e o comentário em `useFinanceData.ts` diz o porquê: sem isso "o saldo pode piscar
   R$ 0,00" se `categories`/`bills` resolverem antes de `accounts`. Offline os snapshots **chegam**
   (vêm do cache do Firestore), mas a janela é a da coleção mais lenta, e no IndexedDB de um celular
   isso é segundos — tempo de sobra pra ler o número errado.
2. **O caminho permanente**: se alguma coleção nunca entrega (offline sem nada em cache pra ela), o
   erro `unavailable` retorna cedo, o listener é mantido vivo de propósito (o SDK retenta quando a
   rede voltar) e `loading` fica `true` **indefinidamente**. Aí o zero também é indefinido.

Nos dois casos vale a mesma conclusão: **enquanto a tela mostra o cache, um valor que escapa do
cache mostra zero.**

Além de errado, o número quebrava a própria conta exibida: a "Sobra prevista" (do cache) **já tinha
somado o saldo**, e a fórmula logo abaixo exibia esse mesmo saldo como R$ 0,00 — `5.500 + 0 − 3.800`
não dá `2.031`. A carta se contradizia à vista.

### A correção

Os dois valores passaram a sair do **mesmo lado do `if`**, num objeto só
(`resolveProjectionView`), em vez de duas expressões independentes que por acaso liam fontes
diferentes. Extraído pra `dashboardViewCache.ts` como função pura e travado com 4 testes — inclusive
um que reproduz o estado exato relatado (cache presente + ao vivo zerado) e outro que verifica que a
fórmula fecha. Era uma linha no meio de um JSX grande: sem função nomeada e teste, a mistura volta
sem ninguém ver.

A mesma troca foi aplicada à `NextMonthProjectionSheet`, que lia os dois valores crus: offline ela
prometeria somar R$ 0,00 e a pessoa desligaria o toggle "contar meu saldo atual" achando que a
opção não funciona.

### Lição, e um erro meu no caminho

**Se uma tela tem modo cache, a regra é "tudo do mesmo lado do `if`"** — um único valor ao vivo no
meio de valores cacheados não é um detalhe, é uma contradição visível, e offline ela não passa
sozinha. Vale auditar o resto do Dashboard com essa lente.

Erro meu: escrevi um comentário JSX **entre atributos** de um componente, o que não é válido. O
`npx tsc --noEmit` avulso que eu vinha rodando passou limpo; quem pegou foi o `npm run build`
(`tsc -b`, com project references). Anotado porque muda o procedimento: **`tsc --noEmit` solto não
substitui o `build` deste projeto** — validar sempre com `npm run build` antes de dar por pronto.

## 2026-08-03 (parte 5) — Varredura do resto do Dashboard com a mesma lente

Pedida pelo dono depois da parte 4. Auditados **todos** os 14 valores que o render consome, cada um
contra o gate de cache que deveria usar. Resultado: 10 já corretos, 3 defeitos, 1 correção de
afirmação minha.

### Achado 1 — "Próximos a receber" não tinha cache nenhum (o mais grave)

`buildUpcomingReceivables(finance.receivables)` era lido **ao vivo**, e `receivables` nunca entrou no
`dashboardViewCache`. Diferente do bug do saldo, não mostrava número errado: a seção só renderiza com
`length > 0`, então ela **sumia inteira** durante o boot. Isso é pior de perceber — some sem deixar
rastro, e é justamente o lembrete de que alguém te deve dinheiro.

Corrigido incluindo `upcomingReceivables` no cache. Chave ausente (cache gravado antes deste deploy)
lê como `[]` **sem invalidar o resto** — mesma tolerância já usada em `nextMonthProjection`. Sem
isso, o primeiro boot depois do deploy jogaria fora o cache de todo mundo e piscaria a tela inteira,
que é exatamente o que esse cache existe pra evitar.

### Achado 2 — estado vazio de "Resumo de gastos" com o gate trocado

A lista usa `financeCache` (só finanças); o estado vazio checava `isCommittedLoading` (finanças **+**
cartão). Com finanças prontas, cartão ainda carregando e a pessoa genuinamente sem gasto no mês, o
corpo do card ficava **em branco** — sem lista e sem estado vazio — até as faturas resolverem. As
outras duas seções (compromissos, transações) já estavam pareadas corretamente; só essa não.

### Achado 3 — `profile!.projectedSalaryCents!` podia render "R$ NaN"

O `if` que mostra a fórmula aceita projeção vinda do **cache**, que sobrevive à remoção do salário
por um render (o cache só é regravado quando o boot termina). Nessa janela as duas asserções `!`
viravam `formatMoney(null)`. Janela estreita e difícil de atingir, mas o custo de fechar era um
`?? 0`.

### O que estava certo (registrado pra não reauditar)

`totalBalanceDisplay`, `committedDisplay`, `effectiveCommittedCaption`, `effectiveSpending`,
`effectiveVariationPct`, `effectiveCommitments`, `effectiveRecent`, `showStartGuide`,
`maxSpendingCents` e `hasPendingCardActivity` (este último é sobre escrita pendente, ler ao vivo é o
correto).

### Testes

Descobri no caminho que já existe `DashboardPage.test.tsx` com contextos mockados — o lugar certo
pro teste de regressão de verdade, renderizando a tela no estado exato do bug em vez de testar só a
função pura. 3 testes novos lá + 2 no cache. **Verificados revertendo as correções**: os dois testes
de regressão falham sem elas, então não são testes que passariam de qualquer jeito.

### Lição

Quando um bug de "fonte misturada" aparece, **a varredura vale mais que a correção pontual**: o
mesmo defeito estava em outros 2 lugares da mesma tela, e o pior deles (a seção que some) nunca teria
gerado uma reclamação — ninguém reclama do que não vê.

## 2026-08-03 (parte 3) — "Tirei o saldo da conta e o Comprometido caiu": o efeito era certo, o aviso é que chegava tarde

Relato do dono, testando ao vivo: marcou o **Nubank** como conta fora do saldo (`excludeFromTotals`,
feature de 02/08 pra vale-refeição) e o **Comprometido despencou**, sem entender a relação. Hipótese
dele na mensagem — *"será nas contas recorrentes que estão vinculadas a essa conta?"* — estava
**exatamente certa**.

### Não era bug de cálculo

`buildUpcomingCommitments` (`financeCalculations.ts`) descarta, por design, as contas a pagar
(`bill.accountId`) e as recorrências (`rule.accountId`) debitadas de uma conta excluída. O motivo é
coerente: se o dinheiro não é contado no Saldo total, subtrair uma obrigação paga com ele faria o
Comprometido descontar algo que o saldo nunca somou, e a sobra da Projeção sairia menor que a
realidade. Para um vale-refeição, certíssimo.

Medido nos dados reais **sem escrever nada** (lendo o contexto do React pela árvore de fibers, não
gravando pra depois desfazer): 6 recorrências do Nubank (Claro, BTS Show, internet, Água, Faculdade,
Colchão) + 1 conta a pagar (meia) = **R$ 1.700,67** saindo do Comprometido de uma vez. As 6
recorrências de **cartão** (R$ 318,21) não se mexem — cartão não é conta, e `card_purchase` nem
grava `accountId`.

### O problema real: a explicação chegava depois do susto

Duas falhas somadas, as duas de UX, nenhuma de matemática:

1. **O gatilho é um ícone de olho** cuja única explicação vivia em `title`/`aria-label` — e num app
   **mobile-first não existe hover**. No dedo, é um olho e mais nada.
2. **A dica que explicava tudo só era renderizada com `hasExcludedAccount === true`** — ou seja,
   aparecia **depois** de a pessoa já ter marcado e levado o susto. Explicação condicionada ao
   estado que ela existe pra evitar.

### A correção

Prévia do efeito antes de agir, com número real — exatamente o padrão `.pay-preview` que a tela de
contas adotou em 02/08 ("dizer o efeito antes de acontecer"). A sheet mostra quanto cai o Saldo
total, quanto cai o **Comprometido** e quantas linhas somem, e diz o que **não** acontece (nada é
apagado, dá pra voltar). A dica de texto passou a aparecer sempre que há conta na tela, não só
depois. Voltar a contar segue em um toque, sem confirmação — é restaurador, não surpreende.

**O número da prévia sai da função real**: `buildUpcomingCommitments` é chamada duas vezes (com e
sem a conta no set de excluídas) e a prévia é a diferença. Reimplementar o filtro na tela daria um
número que começa certo e sai de sincronia no dia em que a regra mudar — o mesmo drift silencioso
que o projeto já pagou entre `signedCharge` e `calculateInvoice`. `invoices`/`cards` vão vazios de
propósito (exclusão não afeta fatura, então se cancelam na subtração); o acoplamento está escrito no
comentário pra não virar armadilha se isso mudar.

Conferido ao vivo: a sheet mostrou **R$ 1.700,67 em 7 linhas**, batendo com o cálculo independente
feito antes. Cancelado sem aplicar — a conta do dono **não** foi alterada.

### Lição

Um controle cujo efeito é grande e **invisível na hora** (cai um número em outra tela) precisa
dizer o efeito antes, com valor real. E vale a regra geral: **texto explicativo condicionado ao
estado que ele existe pra evitar nunca é lido a tempo** — este apareceu só depois de `excludeFromTotals`
já ser `true`.

---

### A mesma correção em `EditTransactionPage` (pedida logo em seguida)

O arquivo-irmão tinha a armadilha idêntica, e a correção foi a mesma. Duas coisas a mais valem
registro:

- **O `await updateCardPurchase` (linha 91) virou fire-and-forget.** Ele era o único lugar da tela
  que *aparentava* tratar erro corretamente — e por isso mesmo **violava a regra offline-first do
  projeto**, travando a UI esperando a rede. Só foi seguro soltar o `await` **depois** que a
  validação síncrona passou a rodar antes: sem ela, trocar `await` por fire-and-forget teria
  transformado o único caminho que dava mensagem em mais um que some em silêncio. A ordem das duas
  mudanças importa.
- **Furo achado na correção da parte 1, fechado nas duas telas.** O fallback de título só age em
  campo **vazio** — um título de **1 letra** passava por ele e ia reprovar no `min(2)` do schema,
  ou seja, voltava a sumir em silêncio pelo caminho que a sessão inteira estava fechando. Agora tem
  mensagem própria ("O título precisa de pelo menos 2 letras — ou deixe em branco pra usar o nome da
  categoria"). **Lição**: ao substituir uma trava por um fallback, mapear a faixa que o fallback
  *não* cobre — "vazio" e "inválido" não são o mesmo conjunto.

### Validação

`typecheck` limpo, **540/540 testes**, build ok. Ao vivo no navegador, nas duas telas: os bloqueios
conferidos um a um (valor vazio, conta ausente, transferência sem origem, título de 1 letra) —
mensagem certa e **sem navegar** em todos —, e o caminho feliz gravou "Delivery" como título, com
ícone e cor da categoria no Extrato.

⚠️ **Os testes ao vivo desta sessão rodaram na conta REAL do dono, não na de teste.** O lançamento
criado na verificação ("Delivery, R$ 50,00") foi excluído em seguida **pela própria UI** — não por
script — justamente pro estorno do saldo passar pelo caminho normal do app: o saldo do dia voltou de
R$ 282,21 pra R$ 332,21 (+50) e o grupo "HOJE" sumiu por não ter mais lançamento. Fica a regra:
**verificação ao vivo que grava dado precisa confirmar em qual conta está antes de gravar**, e
desfazer pela UI, nunca por escrita direta no Firestore (ver o incidente de 31/07 sobre limpeza
manual no banco deixando cache local mentindo).

## 2026-08-03 — Acabamento da reforma: quatro coisas que só aparecem quando alguém usa

A reforma da véspera trocou o padrão de criação das telas de lista. Estes quatro ajustes vieram do
dono **usando** as telas novas — nenhum deles era visível lendo o código, e três são a mesma lição:
**o problema não estava no elemento que eu adicionei, e sim no que sobrou perto dele.**

### O corte que não parecia corte

*"No sheet do contas e assinaturas eu gostei e tals, mas não dá muito a impressão de que tem que
rolar para baixo."*

Medindo a folha aberta no celular (375×812): corpo visível de 588px, conteúdo de 844px — **256px
escondidos, um terço do formulário, incluindo o botão "Criar conta"**. Mas o número não explica a
sensação; a posição do corte explica. Os campos visíveis terminavam assim:

| campo | topo | base |
|---|---|---|
| Vencimento | 692 | **767** |
| *(corte visível)* | | **788** |
| Categoria | **783** | 868 |

O corte caía nos 16px de espaçamento **entre** dois campos. Nenhum pixel de "Categoria" aparecia, e
o formulário terminava numa borda limpa, com respiro embaixo — exatamente o desenho de um formulário
que acabou. **Um corte que cai em espaço vazio não parece corte.** A lição que fica e generaliza: não
confie na "meia linha aparecendo" pra sinalizar rolagem, porque quem decide isso é o espaçamento do
formulário, não você — e ele muda a cada campo condicional.

**A correção foi no `BottomSheet`, não na tela** — a folha de Contas e assinaturas era só a que
doeu primeiro; toda folha do app tem o mesmo risco. Degradê no rodapé (`.sheet-panel--more`) que
apaga sozinho ao chegar no fim, então o aviso só existe enquanto for verdade.

Duas decisões de implementação que valem registro:

- **Vive no `.sheet-panel`, não no `.sheet-body`.** O corpo é o container que rola; um `::after`
  dentro dele rolaria junto com o conteúdo e sumiria da vista justo quando fosse necessário. Preso
  ao painel, ele mora sempre na borda de baixo — e cobre também o padding inferior do painel, por
  isso o degradê fecha em `--bg-surface` cheio: o encontro com o fundo fica invisível.
- **O `ResizeObserver` observa o CONTEÚDO, não só o corpo.** Campo condicional — "Frequência" ao
  marcar recorrente, "Parcelamento" ao escolher cartão — cresce a folha sem o corpo mudar de
  tamanho. Sem isso o aviso ficaria desatualizado exatamente nos formulários mais longos, que são
  os únicos que precisam dele. Provado ao vivo: rolado até o fim (degradê apagado), marcar "Sim,
  recorrente" levou o conteúdo de 844 pra 939px e o aviso **voltou sozinho**.

Descartadas duas alternativas: `mask-image` + scroll-driven animation (Chrome 115+, sem Safari/iOS —
inaceitável num PWA mobile-first que já teve bug de WebKit em iPhone real), e o truque clássico de
`background-attachment: local`, que funciona em todo lugar mas pinta **atrás** do conteúdo — o texto
não desbota, fica em cima de um degradê, que é pior que não ter nada.

### O bloco que ninguém pediu ocupava um terço da folha

Com o degradê no ar, o dono olhou pro que estava gastando o espaço e apontou o bloco de sugestões:
*"tira o sugestão rápida para ganhar espaço"*.

O picker tem **dois estados** e só um deles é palpite: `Sugestões rápidas` (6 serviços fixos, antes
de digitar) e `Encontramos estas opções` (o filtro do que foi digitado). O primeiro é uma aposta
sobre alguém que ainda não disse nada, e cobra 183px no instante em que a folha abre. O segundo
responde ao que a pessoa escreveu, custa **zero** espaço até lá, e é ele que também preenche a
categoria (`selectService`) / o tipo da conta (`selectInstitution`). Então só o estado ocioso saiu.

Auditando o padrão, a tela de **Contas** tinha o gêmeo — e pior: `bank-picker` de **239px** numa
folha que escondia 155. Mesma regra aplicada.

| folha | escondido antes | escondido depois |
|---|---|---|
| Contas e assinaturas → Nova conta | 256px | **56px** |
| Contas → Nova conta financeira | 155px | **0 — cabe inteira** |

Vale notar a ordem em que isso apareceu: o degradê foi feito pra avisar sobre a rolagem, e o efeito
colateral foi **expor o custo** do que estava fazendo a folha rolar. O aviso continua lá pra Contas
e assinaturas (56px ainda escondidos, e agora com a última linha visivelmente cortada); em Contas
ele nunca acende, porque não há mais o que avisar.

### Botão de ajuda: rótulo, não "?"

*"O botão de como funciona deixa igual é na tela de investimentos."* Contas e assinaturas e Dinheiro
a receber usavam `icon-button` redondo só com "?" — Investimentos já tinha o formato bom
(`.button--subtle` + `HelpCircle` + o texto "Como funciona"). Trocados os dois. `.page-heading-actions`
ganhou `flex-wrap`: a linha agora carrega "+ Nova conta", "Como funciona" **e** o badge de sync, e
sem wrap o último item vazaria em tela estreita com fonte grande do sistema. Medido: 119+145 de 343
disponíveis, uma linha só, sem overflow.

### "Já recebido" era um número que não decide nada

Na faixa de Dinheiro a receber, o dono desconfiou do terceiro número. Ele estava certo, por três
motivos que se somam: é **acumulado de sempre**, então só cresce e nunca vira decisão; o dinheiro já
recebido **já está no saldo**, então repeti-lo numa tela sobre o que *falta* entrar sugere que ainda
é pendente; e ele espremia os dois números úteis em um terço de largura cada. Com dois, "A receber"
virou o número grande (`.summary-hero-value--lead`). O histórico não sumiu — o chip "Recebidos" logo
abaixo continua ali.

Regra que fica pra qualquer faixa de resumo: **total acumulado desde sempre quase nunca merece
espaço fixo no topo de uma tela** — ele não responde "o que eu faço agora?", que é a única pergunta
que uma faixa de resumo tem que responder.

### Validação

`typecheck` limpo, **540/540 testes**, build ok. Cada folha foi medida ao vivo no navegador
(`scrollHeight` vs `clientHeight`, antes e depois), o degradê conferido nos dois extremos da rolagem
e no caso do campo condicional, e as folhas curtas (ex.: `SelectField` empilhado, 208=208)
confirmadas **sem** o aviso — ele não acende à toa.

## 2026-08-02 (parte 4) — Reforma visual das telas de lista: o app tinha dois padrões de criação

Pedido do dono, com uma referência concreta em vez de um adjetivo: *"veja o botão de 'nova conta'
na tela de investimento — ao criar uma conta fica de uma maneira clean, fica bonito, tem uma pequena
animação. Queria isso nas outras telas."* Dashboard fora do escopo por pedido explícito ("ela está
ótima").

### O diagnóstico: não era estilo, era outro padrão

O que ele gostou em Investimentos não é um detalhe visual — é um **fluxo diferente**, e o app tinha
os dois convivendo:

| Padrão | Telas | Como era |
|---|---|---|
| **Sheet** | Investimentos, Metas, Categorias | Botão `+` pequeno no cabeçalho → `BottomSheet` sobe de baixo |
| **Acordeão inline** | Contas, Cartões, Contas e assinaturas, Dinheiro a receber | `<form>` estacionado no corpo da página, expandindo no lugar (`.form-accordion-toggle`) |

O acordeão perdia por cinco motivos verificáveis no código, não por gosto:

1. **Ocupava espaço permanente** mesmo fechado. Em A receber e Contas e assinaturas ele era o
   **primeiro** elemento depois do cabeçalho — confirmado ao vivo no navegador: a primeira tela do
   celular mostrava título + texto fixo + card "Adicionar conta" fechado, e **nenhuma conta
   cadastrada**. A lista que a pessoa veio ver começava abaixo da dobra.
2. **Não tinha animação nenhuma** — era `{formOpen && <>...</>}`, render condicional puro. O
   conteúdo aparecia de uma vez e chutava a página pra baixo. Só a seta do `ChevronDown` girava.

### Parte 3 — Idempotência + limpeza de logout (FIN-01/02/03, CLIENT-7)

**Idempotência de pagamento**: `payBill`, `markReceivableReceived` e `recordInvoicePayment` geravam

durante submit. `paidAtRef` no CardDetailPage estabiliza timestamp entre cliques.

**Limpeza de localStorage no logout**: `dashboardViewCache` (saldos/gastos), `pushTokenCache`,
`budgetAlertCache`, `pendingInviteCode` e `defaultCategoriesPrepared` sobreviviam ao logout.

existentes marcados como verificados via Admin SDK. `email_verified` nas regras fica pra depois.

**Admin por custom claims**: `isAdmin()` em `firestore.rules` (7 call sites), `assertAdmin()` em

`RequireAdmin` no client migraram de email hardcoded (`a.thurcos@gmail.com`) para custom claim
`admin: true` no token. Script `scripts/setAdminClaim.mjs` seta o claim. AuthContext expõe `isAdmin`
e `emailVerified`. Deploy order: claim setado ANTES das regras (sem isso = lockout).

### Parte 5 — CSP + Zod webhook + lazy landing + DPO (CLIENT-2, WHATSAPP-02, PERF-2/3, LGPD-01)

**CSP**: `'unsafe-inline'` removido do `script-src`. Substituído por SHA-256 do script inline de

## 2026-08-01 (parte 2) — Investimentos: QA ao vivo do dono, 5 bugs reais + cor por investimento + gráfico redesenhado

Depois da entrega inicial (seção abaixo), o dono testou a feature ao vivo na própria conta e
achou uma sequência de problemas reais — nenhum pego pelo `/review` da entrega original, porque
são de **comportamento em runtime/UX**, não de regra do Firestore. Cada um foi investigado até a
causa raiz antes de corrigir (nunca só o sintoma).

### Achado 1 — Tutorial com layout quebrado

`SlideTour.tsx` (usado por `WelcomeTour`/`AnalysisTour`/`CategoriesTour`/o novo
`InvestmentsTour`) renderizava `position: fixed` **sem portal**, direto na árvore React. O
keyframe `fadeIn` (novo, criado nesta mesma feature) anima `transform: translateY`, e com
`animation-fill-mode: both` o elemento retém esse `transform` depois de terminar — qualquer
`transform` diferente de `none` cria um novo *containing block* pra descendentes
`position: fixed`. O tour ficava confinado ao retângulo da `InvestmentsPage` em vez da tela
inteira. **Fix na raiz**: `SlideTour.tsx` passou a usar `createPortal(..., document.body)`, mesmo
padrão que `BottomSheet.tsx` já usava — conserta os 4 tours de uma vez, não só o de Investimentos,
e blinda qualquer página futura que anime `transform` no `.page` raiz.

### Achado 2 — Categoria sintética vazando no seletor de Nova Transação

A categoria "Investimento: {conta}" (`linkedInvestmentAccountId`) aparecia como opção escolhível
em Nova Transação, quando deveria só aparecer em lançamentos já feitos (Extrato/Análise).
`selectableCategories()` (`categoryHierarchy.ts`) já excluía isso corretamente — o problema é que
`CategoryField.tsx` (o componente real do seletor) **nunca chamava essa função**: reimplementava
a mesma exclusão de pai/filha na mão, de antes desta feature existir, e nunca ganhou a exclusão
de `linkedInvestmentAccountId` quando ela foi adicionada em `selectableCategories`. **Fix**:
`CategoryField.tsx` passou a delegar a `selectableCategories` em vez de duplicar a lógica — e um
teste novo em `categoryHierarchy.test.ts` garante que isso não pode voltar a acontecer.

### Achado 3 — Aportar/Resgatar "sumido"

O botão existia, mas só aparecia depois de expandir manualmente a conta (que nasce recolhida ao
recarregar a página — só a conta *recém-criada* nascia expandida). O dono foi pelo caminho errado
(Nova Transação comum) sem achar o caminho certo. **Fix, três frentes**: contas passam a nascer
**todas expandidas** por padrão (`useEffect` que expande qualquer conta nova, guardando quem foi
recolhido manualmente via `useRef`); investimento criado sem saldo inicial abre o sheet de
Aportar sozinho (fluxo guiado "criar conta → criar investimento → aportar" numa sequência só);
botões de ação ganharam texto visível (antes só ícone com `title` de tooltip).

### Achado 4 — só 1 de 3 investimentos aparecia na lista (achado numa 2ª rodada de teste)

Depois do fix do Achado 3, o dono criou 3 investimentos e só via 1. Causa: a animação de
expandir/recolher usava `maxHeight` calculado por uma fórmula fixa
(`investimentos × 56px + 48px`), calibrada pro design de uma linha só — depois que as linhas
ganharam badge, cor e 3 botões, a altura real ficou bem maior que a estimativa, e o
`overflow: hidden` cortava o resto da lista. **Fix na raiz, não um número maior**: trocado por
`grid-template-rows: 0fr ↔ 1fr` (técnica de CSS que anima accordion sem nunca precisar estimar
altura em px) — essa classe de bug não pode mais acontecer, não importa quanto o conteúdo cresça.

## 2026-08-02 — Conta "fora do saldo" (vale-refeição): a Análise deixa de contar dinheiro que não é dinheiro

Pedido do dono: "quero colocar meu Vale refeição no app, mas ele não é um dinheiro, e não quero que fique entrando junto nas análises". Feature planejada e implementada na mesma sessão.

### As três decisões de produto (fechadas antes de escrever código)

1. **Uma opção só, não duas.** Um toggle por conta ("Não contar no saldo nem nas análises") em vez de um pro saldo e outro pra análise. Modelo mental simples: *"essa conta não é dinheiro"*. A versão de duas opções cobriria casos como "conta de terceiro: some do saldo mas quero ver os gastos" — descartada por não valer o campo extra, a tela extra e o risco de configuração confusa.
2. **O saldo continua visível na tela Contas, com selo.** Não some de tudo: o card da conta mostra o saldo do vale normalmente, com selo "Fora do saldo", e uma linha diz quanto ficou de fora do total. Descartadas: (a) linha extra no Dashboard, que poluiria o hero recém-redesenhado; (b) sumir por completo, que depois de meses deixaria o dono sem entender por que o total não bate com a soma das contas.
3. **Comprometido e Projeção excluem também.** Coerência total: se o dinheiro do vale não conta, a conta fixa debitada dele não vira "comprometido". Sem isso, o Comprometido descontaria uma obrigação que o Saldo total nunca somou, e a sobra da Projeção sairia menor do que a realidade.

### Por que campo novo e não o padrão de `type: 'investment'`

Conta de investimento é removida de `finance.accounts` inteira (`useFinanceData.ts`), o que a tira **também dos seletores de lançamento** — correto pra ela, que não recebe lançamento comum. O vale-refeição precisa do oposto: some dos agregados, **continua** no seletor, porque se lança gasto nele todo dia. Daí `excludeFromTotals?: boolean` (opcional ⇒ ausente = conta normal, zero migração) em vez de um `type` novo.

### Os dois recortes derivados

Em `useFinanceData.ts`, ao lado de `activeAccounts`/`investmentAccounts`:

- `countedAccounts` — contas que somam no Saldo total.
- `excludedAccountIds` — `Set` das marcadas, que os agregados usam pra descartar transação.

`accounts` e `accountBalances` seguem **completos**: tela Contas, seletores e Extrato não mudam nada.

| Some | Continua aparecendo |
|---|---|
| Saldo total (Dashboard + badge de Contas) | Card da conta, com o próprio saldo |
| Donut/lista/histórico/tendência da Análise | Extrato e "Transações recentes" |
| "Resumo de gastos" do Dashboard | Seletor de conta em qualquer lançamento |
| Alertas de orçamento e Resumo Anual | |
| Comprometido e Projeção do próximo mês | |
| Saldo por dia do Extrato (bate com o total) | |

### A trava anti-drift: parâmetro obrigatório, não opcional

`excludedAccountIds` virou parâmetro **obrigatório** em `spendingByCategoryForMonth`, `monthlyTotals`, `spendingByCategoryAcrossMonths`, `calculateDashboardSummary` e `calculateNextMonthProjection`. Um parâmetro opcional aqui significaria que esquecer de passá-lo numa tela nova faria o gasto do vale voltar a contar — sem erro, sem aviso, e invisível pelo mesmo motivo de sempre (offline-first engole o que dá errado). Obrigatório, o TypeScript força cada call site a decidir.

**Isso já pagou na primeira compilação**: o compilador apontou `CategoryTrendSheet.tsx`, que não estava no plano escrito. A tendência por categoria teria continuado somando o vale enquanto o donut ao lado já não somava — dois números diferentes pra mesma categoria, na mesma tela.

Exceção consciente: `buildUpcomingCommitments` tem default vazio, porque vem depois de parâmetros já opcionais e não dá pra torná-lo obrigatório posicionalmente. A disciplina é cobrada um nível acima, onde os dois entrypoints o exigem.

`destinationAccountId` (transferência) ficou de fora de propósito: transferência já não conta como gasto nem receita em nenhuma dessas funções.

Enquanto nenhuma consulta dependeu de filtro, o atalho foi inofensivo; na primeira que dependeu, ele produziu um falso vermelho — e podia ter produzido um falso verde igualmente fácil, escondendo exatamente a classe de bug que este projeto mais paga caro.

## 2026-08-02 (parte 2) — Compra no dia do fechamento caía na fatura que fechava naquele mesmo dia

Achado pelo dono em produção, na própria conta: cartão Nubank fechando dia 2, compra "Cinema" (R$ 61,75) feita no dia 2. A fatura de ago/2026 já aparecia **Fechada** — no app do banco e no Granativa, corretamente — mas a compra do dia tinha caído **dentro dela**, uma fatura fechada vencendo em 8 dias. Reproduzido ao vivo no localhost com a conta real antes de tocar em qualquer código.

### A causa: três regras, três fronteiras diferentes

Não era um erro isolado num arquivo. Três lugares tinham opinião sobre "quando o ciclo acaba", e as três discordavam:

| Onde | O que dizia sobre o dia do fechamento |
|---|---|
| `resolveInstallmentCycle` (`src/cards/cardDates.ts`) | ainda é do ciclo atual (`purchaseDay > closingDay`) → compra do dia entra na fatura que está fechando |
| `closeInvoicesDue` (`functions/src/automation.ts`) | fecha a fatura nesse dia (`referenceMonth <= currentMonth`, rodando quando `closingDay == today`) |
| `markClosedInvoices` (`src/cards/cardService.ts`) | ainda não fechou (`closingDate < todayStart`) |

O servidor fechava a fatura de manhã; o roteamento seguia despejando compra nela; e o cliente, se ninguém tivesse rodado o scheduler, nem a consideraria fechada. O estado que a pessoa via dependia de qual das três tinha falado por último.

### A correção: uma fronteira só

`>` virou `>=` no roteamento e `<` virou `<=` no fechamento do cliente. **O dia do fechamento pertence ao ciclo seguinte, e a fatura fecha nesse dia** — que é como o cartão brasileiro funciona e o que o app do banco mostra. Efeito colateral bom: o cliente passa a fechar a fatura sozinho na data certa, sem depender de o Cloud Scheduler ter rodado.

### A cópia no servidor tinha o mesmo bug

`functions/src/cards/cardDates.ts` é uma **porta manual** de `src/cards/cardDates.ts`, usada por `createCardPurchaseFromMessage.ts` quando a Vic lança compra pelo WhatsApp — e tinha o mesmo `>`. Corrigir só o cliente teria criado um bug pior e mais confuso: lançar a mesma compra pelo app e pelo WhatsApp cairia em faturas diferentes. As duas foram corrigidas no mesmo commit, e cada arquivo ganhou referência cruzada apontando pra outra.

### Lançamento retroativo em fatura fechada: preservado de propósito

Requisito explícito do dono ("não deve impedir também da pessoa se quiser lançar retroativo"). Confirmado que continua funcionando, por dois caminhos independentes:

- O roteamento usa **sempre a data da compra**, nunca "hoje". Compra de 31/jul num cartão que fecha dia 2 → `31 >= 2` → fatura de agosto, mesmo que ela já esteja fechada.
- Nem `validInvoiceLedgerEntryCreate` (`firestore.rules`) nem o client checam o status da fatura antes de gravar. **Fatura fechada não é read-only** — é um rótulo de ciclo, não uma trava.

Travado por teste (`roteia lançamento retroativo pela data da compra, mesmo em fatura já fechada`).

### Por que ninguém pegou antes

Os 9 testes de ciclo que já existiam usavam sempre dias **estritamente** antes ou **estritamente** depois do fechamento. `purchaseDay === closingDay` era a única fronteira que nenhum deles tocava — e é exatamente onde o bug vivia. Nenhum dos 9 mudou de resultado com o `>=`; a correção não quebrou premissa nenhuma, só preencheu o buraco.

Um teste **afirmava explicitamente o comportamento errado** (`não fecha a fatura no próprio dia de fechamento, mesmo à tarde`), com comentário justificando a decisão de design. Foi invertido, e o comentário agora conta por que a realidade desmentiu a premissa.

**Lição**: teste de fronteira precisa cobrir o valor da fronteira, não só os dois lados dela. `<`, `<=`, `>` e `>=` são indistinguíveis por qualquer teste que nunca use o ponto exato — e um comentário convincente em cima da decisão errada faz a lacuna parecer intencional.

### Dado antigo não é migrado

A correção só afeta lançamento novo. A compra "Cinema" continuou na fatura de agosto; o dono ficou de refazer manualmente na conta dele (excluir + relançar — a exclusão estorna certo na fatura fechada via `reverseCardPurchaseOnDelete`).

## 2026-08-02 (parte 3) — Contas a Pagar: as pessoas não entenderam a tela, e o vocabulário era a causa

Relato do dono: *"tem gente achando que tem que colocar só quando vai pagar a fatura do cartão... o nome do botão 'pagar adiantado' e 'pagar' tá confundindo. O intuito dessa tela é bom, mas as pessoas não entenderam."* E o exemplo que define o problema: *"eu sei que se eu coloco Claude dia 15 e clicar em 'pagar' quer dizer que tô falando pro Granativa 'Claude foi creditado do meu cartão, pode gerar a despesa na fatura' — eu sei disso, mas tem gente que não."*

### O diagnóstico: o problema não era o botão, era o verbo

A tela usava vocabulário de **executar** um pagamento, mas o que ela faz é **registrar** um fato que já aconteceu. Isso cria a expectativa errada antes mesmo do primeiro clique — as pessoas esperavam que o app fosse pagar algo, ou que aquilo fosse uma agenda de "o que eu ainda preciso ir lá quitar".

Pior: havia **cinco** palavras diferentes pra mesma coisa, quatro delas na mesma tela.

| Onde | Antes | Como era lido |
|---|---|---|
| Recorrente vencida | `Pago` | rótulo de status, não botão |
| Recorrente a vencer | `Pagar adiantado` | "quero quitar antes do vencimento" |
| Conta avulsa | `Pago` | idem |
| Título da sheet | `Confirmar pagamento` / `Registrar pagamento` | dois nomes pro mesmo passo |
| Atalho do Dashboard | `Compromissos` | **e "Compromissos" também é o nome de uma SEÇÃO dentro da tela** — quem clicava esperando a seção recebia a tela inteira |

### A correção: trocar o eixo de "pagar" para "já foi"

Um rótulo só, **"Já foi paga"**, em voz passiva. A escolha da voz passiva é deliberada e cobre os dois casos reais que um rótulo ativo não cobre junto: a conta de luz que **você** pagou, e a assinatura que o **cartão** foi cobrado (você não pagou nada, e ainda assim "já foi paga" é verdade).

O `Pagar adiantado` sumiu por inteiro. Ele sugeria uma ação *diferente* quando era a mesma confirmação de sempre — e a linha da data logo acima já informa se venceu ou não.

Junto: `Como foi pago?` → **"De onde saiu o dinheiro?"**; `Sem débito` (jargão que ninguém sabia se significava "não paguei" ou "não registra") → **"Não descontar"**; `Confirmar pagamento` → **"Confirmar"**.

### A peça central: dizer o efeito antes de acontecer

A `.pay-preview` no topo da sheet monta a frase com os valores reais, refletindo o que `handleConfirmPay` realmente faz:

- **Cartão** — *"Vamos lançar R$ 30,00 na fatura do Cartão Nubank. Seu saldo em conta não muda agora — muda quando você pagar a fatura."*
- **Conta** — *"Vamos criar a despesa de R$ 30,00 e descontar do saldo de Nubank."*
- **Nenhum** — *"Vamos criar a despesa de R$ 30,00 no seu Extrato, sem descontar de nenhuma conta."*

É o exemplo do Claude dito em voz alta, no momento exato da dúvida, antes do clique. Sem isso, a pessoa só descobria o efeito depois, no Extrato.

### O estado morto que fazia a tela parecer inerte

Fora da janela de 7 dias não existe ação, e isso virava um `Em dia` mudo — na conta do dono, **as 12 recorrentes** apareciam assim ao mesmo tempo. Quem abre a tela longe do vencimento conclui "isso aqui é só uma listinha, não faz nada". Agora diz **"Você confirma a partir de 3 ago"**.

`releaseDateForRecurrence` (novo, `financeService.ts`) deriva da **mesma** `RECURRENCE_EARLY_PAY_DAYS` que `canRegisterRecurrence` usa. Duplicar o cálculo faria a tela prometer uma data e o botão aparecer noutra — divergência que ninguém nota até um usuário reclamar.

### Erro meu no caminho: o texto no lugar errado

Coloquei o "confirme a partir de..." no slot da direita da linha. No desktop passava; **no mobile (375px) quebrava em duas linhas e colidia com os ícones de editar/desativar**. O slot da direita é estreito por natureza — informação de texto pertence ao corpo da linha, que tem largura inteira. Movido pra lá e verificado no viewport real.

### O rename, e o que ele revelou sobre o menu

Investigando o nome, o menu inteiro apareceu como parte do problema:

```
Contas            ← conta bancária
Contas a Pagar    ← conta = boleto/despesa
Contas a Receber  ← conta = boleto/despesa
```

Em português "conta" significa as duas coisas, e o menu usava os dois sentidos em itens adjacentes. Ler "Contas a Pagar" logo abaixo de "Contas" permite entender "as contas [bancárias] que tenho que pagar" — e daí pra "é onde eu pago a fatura do cartão" é um pulo. Ou seja: o mal-entendido relatado começava na navegação, antes de a pessoa abrir a tela.

Decisões do dono, com os custos apresentados antes:

- **"Contas a Pagar" → "Contas e assinaturas"**. Ele preferiu o descritivo mesmo sabendo que mantém três "Contas" no menu — a palavra "assinaturas" sozinha já corrige metade do mal-entendido.
- **"Contas a Receber" → "Dinheiro a receber"** (mesma família descritiva).
- **Atalho do Dashboard: "Compromissos" → "A pagar"**. Primeiro tentei "Assinaturas", e o dono corrigiu na hora, com razão: *"água luz internet etc não é assinatura"*. "A pagar" cobre conta fixa e assinatura igualmente, e não colide com "Contas" (bancárias), que fica na mesma fileira. Bônus: era o rótulo **mais longo** daquele grid — o mesmo que causou o bug do ícone sumindo no iPhone — e virou o mais curto.

**Rotas inalteradas** (`/app/bills`, `/app/receivables`): renomear URL quebraria link salvo e atalho de PWA sem ganho nenhum.

### A tela de Contas a Receber já estava certa

Ao abrir pra renomear, a descoberta: ela **já fazia** tudo o que eu tinha acabado de implementar do outro lado.

| Padrão | Contas a Receber (antes) | Contas a Pagar (antes) |
|---|---|---|
| Linha explicativa sob o título | ✅ | ❌ |
| Verbo em 1ª pessoa/passado | ✅ **"Recebi"** | ❌ "Pago" / "Pagar adiantado" |
| Prévia do efeito na sheet | ✅ | ❌ |

**"Recebi"** é exatamente o mesmo raciocínio de **"Já foi paga"**. O padrão certo já morava no app — só não tinha sido aplicado dos dois lados. Isso é um bom sinal sobre a correção: ela não inventou vocabulário novo, alinhou o app com ele mesmo.

Faltava só o tutorial, adicionado (`ReceivablesTour`, 4 slides). O slide 4 explica o par explicitamente (*"em Contas e assinaturas fica o que VOCÊ deve; aqui fica o que devem A VOCÊ"*), porque as duas telas vinham sendo confundidas entre si.

### Lições

- **Um rótulo ambíguo não se resolve com tutorial.** A ordem certa é: consertar a palavra primeiro, explicar depois. Tutorial que existe pra justificar um botão mal nomeado é band-aid — o botão continua mentindo pra quem pulou o tutorial.
- **Quando o app não executa a ação, o verbo tem que ser passado.** "Pagar" promete que algo vai acontecer; "Já foi paga" confirma que aconteceu. A diferença parece pequena no código e é enorme na cabeça de quem lê.
- **Dizer o efeito antes de confirmar vale mais que qualquer texto de ajuda** — é a única explicação que chega na pessoa no momento em que ela tem a dúvida.
- **Nome de tela é parte da feature.** O mal-entendido tinha origem no menu, não na tela; nenhuma quantidade de copy interna consertaria alguém que nunca chegou a abrir a tela certa.
